# 上下文压缩压测报告

> **TL;DR**：我们构建了一个上下文压缩评测基准（确定性素材 × 开/关压缩两臂对照 × 真实 API）。
> 压测暴露了一个真实缺陷：**重复压缩时旧摘要被整体覆盖，其中只有摘要才知道的关键事实永久丢失**——
> 二次压缩后当场命中率从 100% 掉到 50%，7 次压缩后掉到 0%。
> 修复方案是**滚动摘要**（新摘要必须继承旧摘要），修复后两个场景全程 100%，token 成本仅增加 0.5%~2.6%。
> 对照组（关闭压缩）在半程即因上下文超窗变得不可回答。

---

## 1. 背景与动机

Nova Agent 的上下文压缩（`server/compact.ts`）有三道防线：超大工具输出修剪、接近窗口上限自动总结、溢出后强制压缩重试。
工程实现到位了，但缺一个问题的答案：**"压缩到底好不好用"要拿数据说话**——

- 开压缩比关压缩省多少 token？
- 压缩后模型还记得多少早埋的关键事实？随压缩次数怎么衰减？
- 极端长对话下，关压缩何时变得不可回答？

于是有了这个基准：`scripts/bench/`（约 400 行，零新增依赖）。

## 2. 实验设计

### 2.1 素材：确定性生成，判分不需要 LLM 裁判

`fixtures.ts` 用固定种子生成三类合成长对话（虚构项目"星图数据平台"的例行讨论）：

| 场景 | 素材 | 测什么 |
|---|---|---|
| `fact-recall` | 70 轮对话埋 6 个关键事实（代号/预算/日期/负责人/端口/版本） | 压缩后事实保持率 |
| `constraint` | 早期立两条编码约定（函数前缀 `astro_`、日期库 `nanoid`） | 约束在压缩后是否存活 |
| `overflow` | 200 轮超长对话 | 关压缩何时溢出、开压缩是否可恢复 |

两个关键设计：

1. **事实标记由种子随机生成**（如"玄武-47"式的代号、随机金额/日期）——模型无法凭先验知识猜中，只能从上下文里记住。
2. **判分 = 空白规范化后的字符串匹配**（模型可能写"5 月 26 日"也可能写"5月26日"）——完全确定性，不引入 LLM 裁判的第二重不确定性。

### 2.2 两臂与检查点

- **ON 臂（开压缩）**：逐轮回放素材，每轮按"模拟窗口 × 90%"阈值触发真实的 `compactSession`（复用生产实现，非模拟复刻）；溢出时镜像 `agentLoop` 的恢复路径（强制压缩 keep=6 后重试一次）。
- **OFF 臂（关压缩）**：同样的素材与检查点，但从不压缩，上下文自然增长。
- **检查点**：每 25 轮向模型提问"到当前轮为止埋下的所有事实"，用真实 API 请求回答——这既是能力探针，也如实计量了该时刻的请求成本。
- **当场口径**：命中率只看"该检查点时刻的上下文能否答出"，不做跨检查点并集（并集会把未压缩时答对的算进来，掩盖衰减）。

### 2.3 模拟窗口与溢出语义

实验用 **1536 tokens 的模拟窗口**（阈值 90%），而非真实模型窗口：

- 动机：素材总量约 3K~9K tokens，真实窗口（128K+）下压缩几乎不触发；小窗口让 token 阈值成为主触发机制，等价于"系统提示词+工具定义吃掉大半窗口的小上下文模型"场景。
- 溢出语义：上下文超过模拟窗口的检查点请求**判溢出失败、不再真实调用**（OFF 臂的"死因"）；ON 臂触发溢出恢复路径后重试。
- 该参数可通过 `--window` 调整，机制结论不依赖具体取值。

### 2.4 配置

模型 `deepseek/deepseek-v4-flash`（真实 API）· 窗口 1536 · 阈值 90% · 保留 12 条 · 检查点间隔 25 轮 · 种子 20260101。
同种子同参数下素材完全一致，修复前后两次运行之间**唯一变量是滚动摘要修复**。

### 2.5 复现

```bash
npm run bench:context              # 离线：素材校验 + 压缩调度模拟（零 API 成本）
npm run bench:context -- --online  # 在线：两臂真实对照（少量 API 费用）
npm run bench:rescore -- scripts/bench/out/<run>/results.json  # 判分规则修正后零成本重算
```

## 3. 结果

### 3.1 fact-recall：二次压缩暴露覆盖缺陷

ON 臂当场命中率（6 个事实，压缩发生在第 30、56 轮附近）：

| 检查点 | 压缩累计 | 修复前 | 修复后 |
|---|---|---|---|
| @25 | 0 次 | 100% (3/3) | 100% (3/3) |
| @50 | 1 次 | 100% (6/6) | 100% (6/6) |
| **@71** | **2 次** | **50% (3/6)** | **100% (6/6)** |

修复前 @71 的三个丢失事实（代号/预算/验收时间）全部落在第一次压缩区域，模型的回答是老老实实的**"对话中未提及"**——是摘要被覆盖后的真丢失，不是格式或判分问题；命中的三个恰好落在第二次摘要覆盖区和保留区，与覆盖语义完全吻合。

OFF 臂：@25 尚可回答（上下文 1147 < 窗口），@50 起（2306 > 1536）溢出失败，@71 亦然——**关闭压缩的长对话在半程即不可回答**。

### 3.2 overflow：7 次压缩下的衰减曲线

ON 臂当场命中率（3 个事实，压缩共 7 次）：

| 检查点 | @25 | @50 | @75 | @100 | @125 | @150 | @175 | @200 | @201 |
|---|---|---|---|---|---|---|---|---|---|
| 修复前 | 100% | 100% | 50% | 50% | 33% | 33% | 0% | 0% | 0% |
| 修复后 | 100% | 100% | 100% | 100% | 100% | 100% | 100% | 100% | 100% |

修复前的曲线形状精确呈现覆盖机制：每次压缩"换掉"一份摘要，旧摘要独有的事实随之消失；新近被压缩的事实短暂存活于最新摘要中（@125 的 33% 即新进保留区的那个事实），随后在下次覆盖中消失。

### 3.3 constraint 与 OFF 臂

约束场景中两条编码约定（前缀/库名）经 2 次压缩后依然遵守（摘要继承了约定类信息）；OFF 臂在其唯一存活检查点上同样遵守——约束类信息不如数字类事实脆弱。

### 3.4 token 成本

| 指标（真实 API usage 合计） | 修复前 ON | 修复后 ON | OFF |
|---|---|---|---|
| fact-recall 检查点 input tokens | 4,707 | 4,731 (+0.5%) | 1,357 |
| overflow 检查点 input tokens | 13,797 | 14,152 (+2.6%) | 1,360 |

滚动摘要让每份摘要变大（合并旧摘要），但成本几乎不变。OFF 臂合计更低**没有意义**——它从第 50 轮起无法回答任何问题；压缩买到的是"持续可回答"，这是用关压缩换不来的能力。

## 4. 缺陷与修复

**缺陷**：`compactSession` 每次只总结 `messages` 中被丢弃的部分，然后把 `session.summary` 整体覆盖。
摘要不在消息列表里——第二次压缩时，上一版摘要既不在被总结的内容里，也不在结果里，其中的事实从此无迹可寻。

**修复（滚动摘要）**：`summarizeMessages` 接受 `priorSummary` 参数；`compactSession` 把 `session.summary` 与本次被压缩的消息一起交给 LLM，并在提示词中强制"新摘要必须继承此前摘要中的全部关键事实"。首次压缩行为不变；摘要长度仍受 `SUMMARY_MAX_CHARS` 上限约束，不会无限膨胀。

**回归保护**：`server/__tests__/compact.test.ts` 新增回归测试——mock 捕获 summarize 的完整输入，断言第二次压缩的输入必须包含旧摘要中的事实。

## 5. 局限性

1. **模拟窗口**：1536 tokens 是为让压缩高频触发而设的实验参数，非真实模型窗口；机制结论（覆盖→丢失、滚动→不丢）不依赖窗口取值，但真实场景中的压缩频率与丢失时点会不同。
2. **单模型单种子**：仅测了 deepseek-v4-flash、种子 20260101；`--seed` / `--model` 可扩展，但本文数据未覆盖模型间差异。
3. **探针效应**：检查点提问本身会引导注意力集中到事实回忆上；"任务型"场景（约束遵守）仅覆盖了一条轻量路径。
4. **压缩总结的成本为估算**：`compactSession` 内部的总结调用真实发生，但其 usage 未透出到 bench 层，报告按被压缩消息数粗略估算，未计入上表的 input tokens 合计。
5. **溢出语义为模拟拒绝**：OFF 臂超窗后不再真实调用（省费用且语义清晰）；真实小窗口模型会先报错再走溢出恢复路径，两者的可回答性结论一致，但失败形态不同。

## 6. 结论

- 上下文压缩的价值不在省 token，而在**让长对话持续可回答**（关压缩组半程即溢出全灭）。
- 摘要是有损压缩，**重复压缩的覆盖是隐蔽的信息丢失源**——单元测试发现不了（单次压缩行为正确），只有多次压缩的衰减曲线能暴露它。
- 滚动摘要以 <3% 的额外成本消除了这类丢失；"旧状态必须被显式继承"是所有"覆盖式"状态管理值得自查的一条。
