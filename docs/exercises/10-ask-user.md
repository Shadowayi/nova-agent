## 练习 1（🟢）：服务层为什么"什么都不知道"

**目标**：看懂 `server/askUser.ts` 的解耦边界。

**步骤**：

1. 打开 `server/askUser.ts`，列出它 import 了哪些模块。
2. 回答：ask_user 工具（toolRegistry）是怎么拿到这个服务的？（提示：runtime 字段）
3. 回答：`answer` / `cancel` / `cancelAllForSession` 都调用了同一个 `settle()`——`settle` 做了哪三件事？

**预期结果（自检）**：你能说出——服务零依赖（只 import id 生成）；工具通过 `rt.askUserService`（capability seam）调用；`settle` = 从 `pending` 删 + 从 `bySession` 删（空了删会话索引）+ `resolve` 等待者。这就是"纯状态机可独立单测"的原因。

**提示**：对照指南 §3。

## 练习 2（🟢）：什么时候该问，什么时候不该问

**目标**：建立 ask_user 的使用判断力（这也是给模型的工具描述里的纪律）。

**步骤**：对下面 4 个场景，判断"该问 / 不该问"，一句话说明理由：

1. 用户说"把 README 改成中文"，README 里有一处术语拿不准怎么翻。
2. 用户说"部署到服务器"，但没说是哪台、什么环境。
3. 用户说"继续优化项目"，你正在做上下文压缩，下一阶段选型有 3 个方案但都能推进。
4. 用户说"帮我写一封求职邮件"，邮件抬头称呼不确定用"老师"还是"HR"。

**预期结果（自检）**：2 和 4 该问（缺关键信息，猜了可能全错）；1 可问可不问（拿不准就确认）；3 **不该问**（能自己推进，问 = 打扰）。

**提示**：指南 §0 / §2 的纪律："能自己推进 / 信息已足够时不要问；只有真正卡在需要用户拍板时才问。"

## 练习 3（🟡）：亲手跑一次 ask_user 全流程

**目标**：验证"暂停 → 弹窗 → 回答 → 继续"闭环。

**步骤**：

1. 启动项目（`npm run dev`）。
2. 给 agent 一个必须问你的任务，比如："准备部署 Nova 到一台 Linux 服务器，但你先确认两件事：部署方式（Docker 还是裸机）、要不要顺便配 HTTPS。"（它会调 `ask_user`）
3. 观察：SSE 流"悬停"，弹窗出现（两个问题），回答后 agent 继续当前轮完成。

**预期结果（自检）**：弹窗出现时**没有 done 事件**（流还开着）；提交后模型继续输出；最终回合正常 done。你能说出"暂停的是工具等待，不是 HTTP 连接"。

**提示**：如果 agent 没主动问，可以更直白地要求："调用 ask_user 工具问我两个问题。"（工具始终装配，无需勾选）

## 练习 4（🟡）：取消与中断两条退路

**目标**：验证"取消不是 error"和"中断即清理"。

**步骤**：

1. 让 agent 再问一个问题；这次点弹窗的**取消提问**。
2. 观察模型如何继续（应该换路给建议/结论，而不是报错重试）。
3. 再让 agent 问一个问题；这次不回答，直接点界面上的**停止**（中断 turn）。
4. 回答：`abortRun` 里哪一行代码负责清理挂起提问？（提示：agentLoop.ts，搜 `cancelAllForSession`）

**预期结果（自检）**：取消后 turn 继续、模型换路；中断后 turn 结束、`askUserService.activeCount` 归零（没有幽灵等待）。你能说出两条退路分别由谁触发（用户取消 → answer 路由；会话中断 → abortRun）。

**提示**：指南 §3 / §5。取消走 `POST /answer { cancelled: true }`，中断走 `abortRun` → `cancelAllForSession`。

## 练习 5（🔴）：扩展——给挂起提问加"等待时长进度"

**目标**：实践"服务层扩展 + 前端消费"的解耦路径（模拟 Codex 的 pause timeout progress）。

**步骤**：

1. 给 `AskUserService` 加一个 `peek(sessionId)` 已存在——扩展它返回 `createdAt`（或新增 `getElapsed(sessionId)`），不破坏现有 API。
2. 前端 `AskUserModal` 每 5 秒读一次 `pendingAsk.createdAt`，显示"已等待 X 秒"。
3. 回答：这个扩展需要动服务层吗？（提示：服务层加个字段/方法，工具与路由零改动——这就是解耦的收益）

**预期结果（自检）**：你能加出"等待时长"且 **askUser.test.ts / toolRegistry.test.ts 一条不用改**（新增能力是向后兼容的）。如果你做的时候发现要改旧测试，说明耦合了，回头找耦合点。

**提示**：指南 §7 取舍 1。**先想清 API 再动手**；只加不删。
