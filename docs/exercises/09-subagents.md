## 练习 1（🟢）：注册表字段各管什么

**目标**：读 `server/subagents.ts`，搞清子代理注册表的每个字段在通信里扮演什么角色。

**步骤**：

1. 打开 `server/subagents.ts`，找到 `SubagentRecord` 接口。
2. 逐字段回答：
   - `id` 和 `parentId` 分别是谁？（提示：`send_message` 的"只允许直系"靠什么实现）
   - `inbox` 存的是谁发给谁的消息？什么时候会被消费？
   - `notice` / `notice_consumed` 是给谁看的？"消费"发生在哪一步？

**预期结果（自检）**：你能说出 `parentId` 是"认亲"的关键（决定结算通知投给谁、`to: parent` 认谁当父），`notice` 是"父下一轮要注入的话"，`notice_consumed` 防重复注入。

**提示**：对照 §3（注册表）+ §5（结算通知）读。

## 练习 2（🟢）：三个场景选哪个模式

**目标**：分辨 spawn / fork / background 的适用场景。

**步骤**：给下面三个场景各选一个模式（spawn / fork / background），一句话说明理由：

1. "并行调研 5 个方向，每个方向独立查资料、回来交一份报告"。
2. "刚才我们一起讨论了 Nova 的记忆设计，你去把 discussion 落到 `docs/guide/09.md`"。
3. "帮我盯着那个爬虫任务，可能要好几分钟，你先忙别的，它完成或有进展时再告诉我"。

**预期结果（自检）**：1=spawn（互不相干的并行，自包含 task）；2=fork（要继承刚才的讨论上下文）；3=background（长任务 + 后台 + 完成后通知）。

**提示**：对照 §2 / §3 的模式说明。

## 练习 3（🟡）：亲手派一个后台子代理并观察

**目标**：跑通 background 子代理的创建 → 状态 → 结算通知全链路。

**步骤**：

1. 启动项目（`npm run dev`），在对话里让 agent："用 subagent（background: true）派一个后台子代理去调研 MCP 指数退避重连的用途，然后你继续干别的。"
2. 子代理跑完后，让父 agent 调 `list_agents` 看状态。
3. 再给父 agent 发一句话，观察它是否收到了"子代理有新动态"的结算通知。

**预期结果（自检）**：能亲眼看到——子代理 id（sub_xxx）出现、`list_agents` 从"运行中"变"空闲"、父的下一轮回复里带上了子代理的调研结果。

**提示**：结算通知在**父的下一轮**注入——如果父一直不发言，通知不会自己冒出来。这正是 §5 说的"父必须再发一轮"。

## 练习 4（🟡）：验证"运行中排队"语义

**目标**：确认 `send_message` 到运行中的子不会打断它，而是排队。

**步骤**：

1. 让 agent 派一个后台子代理，任务是"做一个耗时的事"（比如让它 `run_command` 跑一个 sleep/长命令）。
2. 子代理运行中，给父 agent 说："给子代理 sub_xxx 发消息：再补充调研一点。"（父会用 `send_message` 投递）
3. 观察：消息是被立即打断子代理执行，还是排在子代理当前轮之后处理？

**预期结果（自检）**：你能说出——`send_message` 到**运行中**的子只进 inbox 排队，子当前轮结束才处理；到**空闲**的子才会立即启动新轮。对照代码 `pumpSubagent` 的 `while` 循环确认。

**提示**：这是 Nova 与 DSH（AI SDK steer 中途注入）的取舍——排队不打断，代价是不能中途纠偏。

## 练习 5（🔴）：结算通知为什么不能"实时推送"？

**目标**：自己推理出 §5 的设计理由，而不是背答案。

**步骤**：

1. 假设把 settlement notice 改成：子一结束就立刻 `getSession(父id)` → `messages.push(通知)` → `saveSession`。
2. 读 `agentLoop.ts` 的 `runTurn` 结尾和 `server/routes/chat.ts` 的 `saveSession(session)` 调用时机。
3. 构造一个会出问题的时序：父 turn 还在跑、子这时结束了。回答：会发生什么？

**预期结果（自检）**：你能说出——父 turn 结束时路由会用**内存里的父 session 对象**整体 `saveSession`，把"子中途写入 DB 的通知"覆盖掉（通知丢失）。这就是"父的下一轮再注入"消除竞态的原因。

**提示**：`saveSession` 是整个 session 覆盖写，不是 append。先想清"父内存对象 vs DB 里哪个是最终版本"。
